Input Validation & XSS Mitigation

Por que escapar a entrada não basta para impedir XSS?

Pequena aplicação web que mostra os dois hábitos que barram a maior parte das falhas de injeção: validar a entrada contra uma allowlist e codificar a saída para o contexto em que ela é exibida.

Por dentro do projeto

Do problema à solução

Objetivo

Simular um formulário de analista onde usuário, e-mail e uma URL suspeita são enviados para inspeção, e mostrar como cada campo é defendido.

Decisão principal

A primeira versão escapava os dados assim que chegavam. Funcionava numa página, mas o valor guardado virava HTML: quebrava em URL, JSON ou SQL e era escapado duas vezes. A versão atual guarda o valor original, rejeita o que não bate com a allowlist e escapa só na hora de renderizar.

Camadas de defesa

Allowlist com regex e FILTER_VALIDATE_EMAIL, URLs aceitas só com esquema http/https (javascript: e data: são barradas), token CSRF comparado com hash_equals() e uma CSP sem scripts inline como segunda camada.

O que aprendi

Escapar não é validar: htmlspecialchars() deixa o dado seguro para HTML, não seguro em geral. Allowlists são mais fortes que blocklists. E a CSP segura o ataque mesmo se um bug de codificação passar.
