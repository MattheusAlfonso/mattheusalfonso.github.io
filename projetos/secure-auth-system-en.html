Secure Authentication System

How does a login withstand brute force, session hijacking and CSRF?

A login → restricted dashboard → logout flow built to show the controls behind secure authentication: password hashing, session hardening, centralized access control, brute-force protection and CSRF defense.

Inside the project

From problem to solution

Goal

Show, in a small and testable flow, the controls the OWASP Top 10 asks for in A01 (Broken Access Control) and A07 (Identification & Authentication Failures).

How it works

The password is stored only as a bcrypt hash (cost 12). After login the session ID is regenerated, cookies are set with HttpOnly and SameSite=Strict, and the session expires after 5 min idle or 30 min in total.

Security decisions

The attempt counter lives on the server, not in the session: otherwise dropping the cookie would reset it. password_verify() runs even for unknown users, so response time does not reveal which usernames exist. The dashboard shows only a SHA-256 session fingerprint, never the real ID.

Defense tests

Opening /dashboard.php without logging in redirects. 5 wrong passwords lock you out for 15 minutes, even after deleting cookies. Logout via GET returns 405 and login without a CSRF token returns 403.
