Input Validation & XSS Mitigation

Why isn't escaping input enough to stop XSS?

A small web app that shows the two habits that stop most injection bugs: validate input against an allowlist and encode output for the context where it is displayed.

Inside the project

From problem to solution

Goal

Simulate an analyst form where a username, an e-mail and a suspicious URL are submitted for inspection, and show how each field is defended.

Key decision

The first version escaped data as soon as it arrived. It worked on one page, but the stored value became HTML: it broke in URLs, JSON or SQL and got double-escaped. The current version keeps the original value, rejects what fails the allowlist and escapes only when rendering.

Defense layers

Allowlist with regex and FILTER_VALIDATE_EMAIL, URLs accepted only with an http/https scheme (javascript: and data: are blocked), a CSRF token checked with hash_equals() and a CSP with no inline scripts as a second layer.

What I learned

Escaping is not validation: htmlspecialchars() makes data safe for HTML, not safe in general. Allowlists beat blocklists. And CSP stops the attack even if an encoding bug slips through.
